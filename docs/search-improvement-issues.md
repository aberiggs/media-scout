# Search improvement issues

Initial capture: 2026-10-07. This is a durable issue log, not a redesign specification or a claim that the listed work is implemented. Source observations: `docs/general-search.md`, `src/core/general-search-conversation.ts`, `src/core/general-search.ts`, `src/settings.ts`, `src/daemon.ts`, and the focused tests `tests/general-search-conversation.test.ts`, `tests/general-search.test.ts`, and `tests/settings.test.ts`. UI observations were reported by the user/recon and have not been independently validated here.

Status key: **Open** = needs investigation or implementation; **In progress** = partial implementation with explicit remaining work; **Evidence needed** = hypothesis or user observation that needs reproduction. Priorities are relative.

## Decision log

- Prefer **search-first, results-dominant, optional refinement** over turning general search into a chatbot. Conversation is a means to clarify/refine discovery, not the primary product surface.
- MCP is not a prerequisite for improving search UX or search intelligence. Existing MCP behavior and its approval/safety semantics are separate concerns.
- Keep bounded backend behavior and explicit user control; do not trade understandable progress or safety for an unbounded agent loop.

## Evidence to collect

For UI issues, capture the affected view and viewport, interaction sequence, and busy/idle state. For search quality, retain sanitized original request, planner queries, provider/indexer outcome, candidate/filter counts, and resulting UI state. For refusal/error reports, capture only sanitized status/error classification and enough reproduction details to distinguish provider refusal from transport or configuration failures. Add focused regression tests for each confirmed behavior before marking an issue resolved.
